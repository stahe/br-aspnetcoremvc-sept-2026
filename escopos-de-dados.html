    6. Escopos de dados

    Uma aplicação web atende muitos usuários ao mesmo tempo, e cada usuário faz numerosas requisições. Os dados podem, portanto, ser compartilhados em três níveis, conhecidos como seu escopo:

    • Escopo de aplicação: os dados são compartilhados por todos os usuários durante todo o tempo de vida do servidor (a lista de médicos, por exemplo);
    • Escopo de requisição: os dados existem apenas durante uma requisição (o modelo de uma view);
    • Escopo de cliente: os dados são específicos de um usuário e devem persistir de uma requisição para a seguinte (o idioma selecionado, o usuário logado).

    O curso original ([ASP.NET MVC], 2013) usava uma sessão para este último escopo: um espaço de memória, mantido pelo servidor, específico de cada navegador. O [ASP.NET Core] ainda usa essa abordagem ([AddSession]), mas este documento, assim como o estudo de caso, dispensa esse recurso: os dados de escopo de cliente são armazenados pelo navegador em cookies. O servidor não retém nenhum dado entre as requisições de um mesmo usuário: diz-se que ele não mantém estado ([stateless]). É isso que torna possível, por exemplo, executar vários servidores idênticos atrás de um balanceador de carga. A contrapartida: um cookie está sob o controle do usuário, que pode lê-lo e modificá-lo. Por isso, só são armazenados ali dados não sensíveis — ou dados assinados ou criptografados pelo servidor, que pode então detectar qualquer modificação: é o caso do cookie do [TempData] (Exemplo 20) e do token de autenticação (Capítulo 8).

    No lado do servidor, os escopos de aplicação e de requisição correspondem aos ciclos de vida dos serviços de injeção de dependência (veja o Exemplo 06). O [ASP.NET Core] tem três deles:

    Registro
    Ciclo de vida
    Uma instância...
    AddSingleton
    aplicação
    durante todo o tempo de vida da aplicação, compartilhada por todas as requisições
    AddScoped
    requisição
    por requisição HTTP, compartilhada por todos que a solicitam durante essa requisição
    AddTransient

    namespace Example23.Services;

// escopo de APLICAÇÃO (AddSingleton): uma única instância, compartilhada por
// TODAS as requisições de TODOS os usuários
public class CounterService
{
    private int total;

    // várias requisições podem ser executadas AO MESMO TEMPO: Interlocked
    // garante que dois incrementos simultâneos não se percam
    public int Increment() => Interlocked.Increment(ref total);
}
    • Linha 7: o serviço será um singleton (veja [Program.cs]): seu campo [total] tem, portanto, escopo de aplicação;
    • linha 11: um servidor web processa várias requisições simultaneamente, em várias threads ([threads]). Se duas requisições executam [total++] ao mesmo tempo, ambas podem ler o mesmo valor, e um incremento é perdido. [Interlocked.Increment] realiza a leitura, a soma e a escrita em uma única operação indivisível. Um serviço singleton deve sempre se precaver contra esses acessos simultâneos.

    namespace Example23.Services;

// escopo de REQUISIÇÃO (AddScoped): uma NOVA instância para cada requisição HTTP,
// compartilhada por todos que a solicitam DURANTE essa requisição
public class RequestService
{
    private static int createdInstances; // static: um contador compartilhado por todas as instâncias

    public int Number { get; } = Interlocked.Increment(ref createdInstances);
}
    • linha 7: um campo declarado como [static] pertence à classe, não a uma instância; ele é compartilhado por todas as instâncias. Ele conta o número de instâncias criadas;
    • linha 9: cada instância recebe um número ao ser criada. O serviço terá escopo de requisição: o número muda a cada requisição.

    using System.Text.Encodings.Web;
using System.Text.Unicode;
using Example23.Services;
using Microsoft.Extensions.FileProviders;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddControllersWithViews();
builder.Services.AddSingleton(HtmlEncoder.Create(UnicodeRanges.All));
// os três tempos de vida de um serviço
builder.Services.AddSingleton<CounterService>(); // uma instância para toda a aplicação
builder.Services.AddScoped<RequestService>();    // uma instância por requisição
builder.Services.AddTransient<ToolService>();    // uma instância por injeção

var app = builder.Build();

app.UseStaticFiles(new StaticFileOptions
{
    FileProvider = new PhysicalFileProvider(Path.GetFullPath(Path.Combine(builder.Environment.ContentRootPath, "..", "common", "bootstrap"))),
    RequestPath = "/bootstrap",
});

// escopo de REQUISIÇÃO: HttpContext.Items nasce e morre com a requisição
app.Use(async (context, next) =>
{
    context.Items["start"] = DateTime.Now.ToString("HH:mm:ss.fff");
    await next(context);
});

app.MapControllers();
app.Run();

Tudo o que processa a requisição (filtros, controller, view) pode ler e escrever nele. É o equivalente de [res.locals]* no [Express].

    using Example23.Services;
using Microsoft.AspNetCore.Mvc;

namespace Example23.Controllers;

public record ScopesModel(int Total, int Instance, int Tool, int MyVisits);

public class ScopesController(CounterService counter, RequestService request, ToolService tool) : Controller
{
    [HttpGet("/")]
    public IActionResult Scopes()
    {
        // escopo de CLIENTE: um dado mantido pelo NAVEGADOR (cookie),
        // reenviado ao servidor a cada requisição
        int.TryParse(Request.Cookies["myVisits"], out var myVisits);
        myVisits++;
        Response.Cookies.Append("myVisits", myVisits.ToString(),
            new CookieOptions { HttpOnly = true, SameSite = SameSiteMode.Lax });
        return View(new ScopesModel(counter.Increment(), request.Number, tool.Number, myVisits));
    }
}
    • linha 8: os três serviços são injetados;
    • linhas 15–18: o escopo de cliente: um contador armazenado em um cookie. [Request.Cookies["myVisits"]] lê o cookie enviado pelo navegador ([null] na primeira visita). [int.TryParse] o converte em inteiro; se a conversão falhar, [myVisits] recebe 0. A action o incrementa e redefine o cookie;
    • linha 19: os valores são passados à view.

    Para um contador de visitas, isso é irrelevante. Para dados sensíveis (a identidade do usuário, seu papel), o servidor precisa ser capaz de detectar adulterações: o Capítulo 8 mostra como.

    Dessas durações decorre uma regra: um serviço não deve depender de um serviço com ciclo de vida mais curto. Um singleton que receba um serviço como [Scoped] o manteria indefinidamente, bem além da requisição para a qual ele foi criado. O [ASP.NET Core] verifica o cumprimento dessa regra na inicialização, em modo de desenvolvimento, e se recusa a iniciar se ela for violada. No estudo de caso:
