    2. Controllers, actions, roteamento

    Este capítulo examina o caminho percorrido por uma requisição, do navegador até a action que a processa, e a resposta que essa action devolve. As views só serão apresentadas no Capítulo 4: aqui, as actions devolvem texto ou JSON diretamente.

    // o "builder" da aplicação: configuração, logging, serviços...
var builder = WebApplication.CreateBuilder(args);

// registra os serviços de que o MVC precisa para encontrar e executar os controllers

    Vamos analisar este código:

    • Linha 2: [WebApplication.CreateBuilder] cria o “construtor” da aplicação. Ele lê a configuração (o arquivo [appsettings.json], as variáveis de ambiente etc.), configura o log e prepara a lista de serviços da aplicação, [builder.Services]. O parâmetro [args] contém os argumentos da linha de comando;
    • linha 5: os serviços de que o [MVC] precisa para localizar os controllers da aplicação e executar suas actions são adicionados à lista;
    • linha 8: a aplicação é construída. Depois desta linha, a lista de serviços não pode mais ser modificada;
    • linha 11: as rotas declaradas pelos controllers (os atributos [[HttpGet]], [[Route]]..., sobre os quais falaremos) são habilitadas: sem esta linha, nenhuma action seria chamada;
    • linha 14: inicia o servidor web [Kestrel] e aguarda requisições até que a aplicação seja encerrada ([Ctrl-C]). Salvo indicação em contrário, o servidor escuta na porta 5000.

    Este arquivo não contém nenhuma classe nem nenhum método chamado [Main]: é um programa de instruções de nível superior. O próprio compilador [C#] envolve essas instruções em um método chamado [Main], que serve de ponto de entrada do programa. Observe também a ausência de diretivas [using]: [WebApplication] pertence ao namespace [Microsoft.AspNetCore.Builder], que é importado automaticamente (veja [ImplicitUsings] na introdução).

    using Microsoft.AspNetCore.Mvc;

namespace Example01.Controllers;

// um controller é uma classe que herda de Controller
public class HomeController : Controller
{
    // uma action: o método chamado para a requisição GET /
    [HttpGet("/")]
    public string Index()
    {
        // o valor retornado pela action é a resposta enviada ao navegador
        return "Hello from ASP.NET Core MVC!";
    }
}
    • Linha 1: o namespace que contém a classe [Controller] e os atributos do [MVC];
    • linha 3: o namespace das classes deste arquivo. Por convenção, ele inclui o nome do projeto ([Example01]) e o diretório do arquivo ([Controllers]). A forma [namespace X;] (sem chaves) vale para o arquivo inteiro;
    • linha 6: um controller é uma classe public que herda da classe [Controller]. Por convenção, seu nome termina com [Controller]. O [ASP.NET Core] encontra automaticamente os controllers da aplicação — não é preciso declará-los;
    • linha 9: o atributo [[HttpGet("/")]] associa o método [Index] às requisições [GET /]. Um método associado dessa forma a uma rota é uma action. Um atributo [C#] é escrito entre colchetes, imediatamente antes do elemento que descreve: ele adiciona informações ao método, que o framework lê na inicialização;
    • Linha 13: o valor devolvido pela action é a resposta enviada ao navegador.

    using Microsoft.AspNetCore.Mvc;

namespace Example02.Controllers;

public class HomeController : Controller
{
    // GET /: uma página HTML contendo links para as outras actions
    [HttpGet("/")]
    public ContentResult Index()
    {
        const string html = """
            <h2>Example 02 - routing</h2>
            <ul>
              <li><a href="/first">/first</a></li>
              <li><a href="/first/action01">/first/action01</a></li>
              <li><a href="/first/products/17">/first/products/17</a></li>
              <li><a href="/first/products/17/reviews/3">/first/products/17/reviews/3</a></li>
              <li><a href="/first/files/images/logo.png">/first/files/images/logo.png</a></li>
              <li><a href="/first/products/abc">/first/products/abc</a></li>
              <li><a href="/unknown">/unknown</a></li>
            </ul>
            """;
        // Content(text, type): uma resposta cujo tipo nós escolhemos (aqui, HTML)
        return Content(html, "text/html; charset=utf-8");
    }
}
    • linha 9: a action não devolve mais uma string, e sim um [ContentResult]: uma resposta cujo conteúdo e tipo são especificados;
    • linhas 11–22: uma string bruta [C#] ([raw string literal]), delimitada por três aspas. Ela pode se estender por várias linhas e conter aspas sem precisar escapá-las. Os espaços que precedem o ["""] de fechamento são removidos de cada linha;
    • linha 24: o método [Content(text, type)] da classe [Controller] gera um [ContentResult]. O tipo [text/html] instrui o navegador a interpretar o texto como HTML.

    A action [Index] devolve, portanto, uma página HTML que contém links para as actions do outro controller:

    using Microsoft.AspNetCore.Mvc;

namespace Example02.Controllers;

// prefixo compartilhado por todas as rotas do controller
[Route("first")]
public class FirstController : Controller
{
    // GET /first
    [HttpGet("")]
    public string Index()
    {
        return "Action [Index] of the [First] controller";
    }

    // GET /first/action01
    [HttpGet("action01")]
    public string Action01()
    {
        return "Action [Action01] of the [First] controller, GET request";
    }

    // POST /first/action01: mesmo caminho, outro método HTTP
    [HttpPost("action01")]
    public string Action01Post()
    {
        return "Action [Action01Post] of the [First] controller, POST request";
    }

    // GET /first/products/17: {id} é um parâmetro de rota, ":int" uma restrição
    [HttpGet("products/{id:int}")]
    public string Product(int id)
    {
        return $"Product no. {id}";
    }

    // GET /first/products/17/reviews/3: dois parâmetros de rota
    [HttpGet("products/{id:int}/reviews/{number:int}")]
    public string Review(int id, int number)
    {
        return $"Review no. {number} of product no. {id}";
    }

    // GET /first/files/...: {**path} aceita qualquer final de caminho
    [HttpGet("files/{**path}")]
    public string File(string path)
    {
        return $"Requested file: {path}";
    }
}

    Vamos analisar este código:

    • linha 6: o atributo [[Route("first")]], aplicado à classe, define o prefixo comum a todas as rotas do controller: suas actions tratam as rotas de URL que começam com [/first];
    • linhas 10–11: [[HttpGet("")]]: a action [Index] trata [GET /first]. A URL de uma action é a concatenação do prefixo do controller com o caminho da action;
    • linhas 17–18: a action [Action01] processa [GET /first/action01];
    • linhas 24–25: o mesmo caminho, mas para o método POST: [[HttpPost]] substitui [[HttpGet]]. Existem também [[HttpPut]], [[HttpDelete]], [[HttpPatch]]... O nome do método [C#] ([Action01Post]) é arbitrário: para o roteamento, só importam os atributos. Além disso, dentro da mesma classe, dois métodos não podem ter o mesmo nome com os mesmos parâmetros;
    • linhas 31–32: [{id}] é um parâmetro de rota: esse segmento da URL pode assumir vários valores. [:int] é uma restrição: o segmento deve ser um número inteiro; caso contrário, a rota não corresponde. O valor do segmento é passado ao parâmetro de mesmo nome da action, [id], já convertido para [int]: para [/first/products/17], [id] é igual ao número 17. Esse é o model binding ([model binding]), que o próximo capítulo examinará em detalhes;
    • linhas 38–39: dois parâmetros de rota, passados a dois parâmetros da action;
    • linhas 44–46: [{**path}] é um parâmetro "catch-all" ([catch-all]): aceita qualquer final de URL, inclusive [/].

    using Microsoft.AspNetCore.Mvc;

namespace Example03.Controllers;

[Route("responses")]
public class ResponsesController : Controller
{
    // uma string: enviada como está, com o tipo [text/plain]
    [HttpGet("text")]
    public string Text()
    {
        return "<h1>Action [Text]</h1>";
    }

    // a mesma string, anunciada como HTML: o navegador a interpreta
    [HttpGet("html")]
    public ContentResult Html()
    {
        return Content("<h1>Action [Html]</h1>", "text/html; charset=utf-8");
    }

    // um objeto: serializado em JSON, com o tipo [application/json]
    [HttpGet("json")]
    public object Json()
    {
        return new { lastName = "Martin", firstName = "Jean", age = 42 };
    }

    // um array: também serializado em JSON
    [HttpGet("array")]
    public string[] Array()
    {
        return ["Mme", "Melle", "Mr"];
    }

    // IActionResult: a action escolhe a resposta completa (código, conteúdo)
    // StatusCode(201, ...): o código 201 (Created) em vez de 200 (OK)
    [HttpGet("created")]
    public IActionResult ResourceCreated()
    {
        return StatusCode(201, new { message = "resource created" });
    }

    // sem resposta: o código 204 (No Content) significa "nada a exibir"
    [HttpGet("empty")]
    public IActionResult EmptyResponse()
    {
        return NoContent();
    }

    // uma action assíncrona: o ASP.NET espera o fim da tarefa (Task)
    [HttpGet("task")]
    public async Task<object> AsyncTask()
    {
        var start = DateTime.Now;
        await Task.Delay(500); // uma espera de 500 ms, sem bloquear o servidor
        return new { wait = $"{(DateTime.Now - start).TotalMilliseconds:0} ms" };
    }

    // um erro "esperado": NotFound(...) produz uma resposta 404
    [HttpGet("not-found")]
    public IActionResult NotFoundError()
    {
        return NotFound(new { message = "This resource does not exist" });
    }

    // um erro "inesperado": uma exceção não tratada produz uma resposta 500
    [HttpGet("exception")]
    public string Exception()
    {
        throw new InvalidOperationException("An unexpected error");
    }
}

    Vamos analisar este código:

    • linhas 9–12: uma string é enviada como está, com o cabeçalho [Content-Type: text/plain; charset=utf-8];
    • linhas 16–19: a mesma string, declarada como HTML (veja o Exemplo 02): o navegador a interpreta;
    • linhas 23–26: um objeto é serializado como JSON, com o cabeçalho [Content-Type: application/json]. [new { lastName = ..., firstName = ... }] cria um objeto de um tipo anônimo: um tipo sem nome gerado pelo compilador, útil para dados usados uma única vez. Os nomes das propriedades do JSON são escritos em “camelCase” (primeira letra minúscula), seguindo a convenção do [JavaScript];
    • linhas 30–33: um array também é serializado como JSON. [["Mme", "Melle", "Mr"]] é uma expressão de coleção ([C#] 12), que aqui cria um array de strings;
    • linhas 39–41: quando a action precisa escolher o código de status, ela devolve um [IActionResult]: um objeto que descreve a resposta completa. Os métodos da classe [Controller] geram muitos deles: [StatusCode(201, object)] produz uma resposta de código 201 ([Created]) cujo conteúdo é o objeto serializado em JSON;
    • linhas 46–48: [NoContent()] devolve o código de status 204 ([No Content]): “sem conteúdo”;
    • linhas 53–57: uma action pode ser assíncrona ([async]): ela então devolve uma tarefa ([Task<T>]), o equivalente a uma promise ([JavaScript]), e o [ASP.NET Core] espera a conclusão da tarefa antes de responder. [await Task.Delay(500)] espera 500 ms sem bloquear o servidor: durante a espera, a thread que executava a action é devolvida ao servidor, que pode usá-la para processar outras requisições. É assim que se escrevem todas as actions que consultam um banco de dados;
    • linhas 62–64: um erro previsto pelo programa: [NotFound(object)] devolve uma resposta 404 com conteúdo JSON. Da mesma forma, existem [BadRequest(...)] (400), [Unauthorized()] (401), [Forbid()] (403), [Ok(...)] (200)...;
    • linhas 69–71: um erro inesperado: a action lança uma exceção, que ela não trata. O [ASP.NET Core] responde então com um erro 500 ([Internal Server Error]).

    2.4. Exemplo 04: Redirecionamentos

    Uma action pode responder com um redirecionamento: um código de status 301 ou 302 e um cabeçalho [Location] que informa ao navegador qual URL solicitar em seguida. O navegador a solicita imediatamente, sem nenhuma intervenção do usuário. Os redirecionamentos são onipresentes em uma aplicação web: após o envio bem-sucedido de um formulário, após o login, após a troca de idioma...

    using Microsoft.AspNetCore.Mvc;

namespace Example04.Controllers;

public class RedirectsController : Controller
{
    // redirecionamento permanente (301): a página mudou de endereço definitivamente
    [HttpGet("old")]
    public IActionResult OldPage()
    {
        return RedirectPermanent("/new");
    }

    [HttpGet("new")]
    public string NewPage()
    {
        return "You are on the [new] page";
    }

    // redirecionamento temporário (302), para um endereço calculado
    [HttpGet("go/{destination}")]
    public IActionResult Go(string destination)
    {
        return Redirect($"/page/{destination}");
    }

    // redirecionamento para uma ACTION: o ASP.NET constrói a URL por conta própria
    [HttpGet("to-action/{destination}")]
    public IActionResult ToAction(string destination)
    {
        return RedirectToAction(nameof(Page), new { name = destination });
    }

    [HttpGet("page/{name}")]
    public string Page(string name)
    {
        return $"You are on the [{name}] page";
    }

    // redirecionamento para outro site
    [HttpGet("documentation")]
    public IActionResult Documentation()
    {
        return Redirect("https://learn.microsoft.com/aspnet/core");
    }
}

    Vamos analisar este código:

    • linhas 9–11: [RedirectPermanent(url)] gera um redirecionamento permanente (código de status 301, [Moved Permanently]): o endereço da página mudou definitivamente. Navegadores e mecanismos de busca podem armazenar o novo endereço em cache;
    • linhas 22–24: [Redirect(url)] gera um redirecionamento temporário (código de status 302, [Found]), neste caso para um endereço calculado. [$"/page/{destination}"] é uma string interpolada: a expressão entre chaves é substituída pelo seu valor;
    • linhas 29–31: [RedirectToAction(action, values)] redireciona para uma action, não para uma URL: o [ASP.NET Core] mesmo gera a URL da action [Page] com base em sua rota ([page/{name}]) e nos valores fornecidos ([name = destination]). Se o caminho da action mudar um dia, o redirecionamento o acompanha. [nameof(Page)] devolve o nome do método (["Page"]): um erro de digitação causaria um erro de compilação, o que não acontece com uma string escrita à mão;
    • linhas 42–44: é possível redirecionar para outro site.

    2.5. Exemplo 05: Os objetos de requisição e de resposta

    Cada requisição é representada por um objeto [HttpContext], que contém a requisição ([Request]) e a resposta que está sendo gerada ([Response]). Uma action acessa esse objeto diretamente pelas propriedades [HttpContext], [Request] e [Response] da classe [Controller]. Isso às vezes é necessário, e o faremos no estudo de caso (para ler ou definir um cookie, por exemplo), mas é preciso saber o que se está fazendo.

namespace Example05.Controllers;

[Route("http")]
public class HttpController : Controller
{
    // a requisição: método, caminho, parâmetros, cabeçalhos...
    [HttpGet("request")]
    public object RequestInfo()
    {
        return new
        {
            method = Request.Method,
            path = Request.Path.Value,
            parameters = Request.QueryString.Value,
            browser = Request.Headers.UserAgent.ToString(),
            ip = HttpContext.Connection.RemoteIpAddress?.ToString(),
        };
    }

    // a resposta: adicionamos um cabeçalho a ela e depois a action retorna seu valor normalmente
    [HttpGet("header")]
    public string Header()
    {
        Response.Headers["X-Example"] = "05-httpcontext";
        return "Response with an added header";
    }

    // a resposta escrita "à mão": código, tipo e depois o corpo
    [HttpGet("response")]
    public async Task ResponseByHand()
    {
        Response.StatusCode = 200;
        Response.ContentType = "text/plain; charset=utf-8";
        await Response.WriteAsync("Response written by [Response.WriteAsync]");
    }

    // ERRO a não cometer: escrever a resposta E DEPOIS retornar um resultado
    [HttpGet("double")]
    public async Task<IActionResult> Double()
    {
        await Response.WriteAsync("Start of the response... ");
        // a resposta já saiu: seu código e seus cabeçalhos não podem mais mudar
        return NotFound();
    }
}

    Vamos analisar este código:

    • linhas 10–18: a requisição: o método HTTP ([Request.Method]), o caminho ([Request.Path]), os parâmetros da URL ([Request.QueryString]), os cabeçalhos ([Request.Headers]) e, por meio de [HttpContext.Connection], o endereço (IP) do cliente. [?.] é o operador “condicional nulo”: se [RemoteIpAddress] for igual a [null], a expressão é avaliada como [null] em vez de causar um erro;
    • linhas 24–27: a action adiciona um cabeçalho à resposta e depois devolve normalmente o valor dela, que o [ASP.NET Core] envia. É o uso mais comum de [Response];
    • linhas 32–36: a action escreve a resposta por conta própria — código de status, tipo e, em seguida, o corpo — usando [Response.WriteAsync]. Ela não devolve nada ([Task], e não [Task<T>]);
    • linhas 41–45: o erro a evitar: escrever parte da resposta e depois devolver um resultado. Depois que os primeiros bytes do corpo foram enviados ao navegador, o código de status e os cabeçalhos — que foram enviados antes do corpo — não podem mais ser alterados.

// uma IMPLEMENTAÇÃO do contrato: aqui, dados em memória

    using Microsoft.AspNetCore.Mvc;

namespace Example06.Products;

[Route("products")]
public class ProductsController : Controller
{
    private readonly IProductsService productsService;

    // injeção de dependência: o ASP.NET fornece a implementação de IProductsService
    public ProductsController(IProductsService productsService)
    {
        this.productsService = productsService;
    }

    [HttpGet("")]
    public IReadOnlyList<Product> List()
    {
        return productsService.FindAll();
    }

    [HttpGet("{id:int}")]
    public IActionResult OneProduct(int id)
    {
        var product = productsService.FindById(id);
        if (product is null)
        {
            return NotFound(new { message = $"Product no. {id} not found" });
        }
        return Ok(product);
    }
}
    • linhas 11–13: injeção de dependência. O controller declara, em seu construtor, que precisa de um [IProductsService]; o [ASP.NET Core] fornece a ele o objeto registrado para esse tipo (veja abaixo). O controller nunca chama [new ProductsService()]: ele nem sequer conhece essa classe, apenas a interface. A implementação poderia ser substituída (por uma versão que lê um banco de dados ou por uma versão de teste) sem modificar o controller;
    • linhas 17–19: a action delega ao serviço. A lista é serializada em JSON;
    • linhas 23–30: [{id:int}] converte o identificador; um produto inexistente devolve uma resposta 404. [Ok(object)] devolve uma resposta 200 cujo conteúdo é o objeto serializado em JSON. [is null] verifica se um valor é nulo.

    2.6.6. Registro dos serviços

    O [ASP.NET Core] só pode fornecer um serviço se o conhecer: cada serviço é registrado em [builder.Services], junto com seu tempo de vida. O arquivo [Products/ProductsExtensions.cs]:

     1
 2

    namespace Example06.Products;

// um "método de extensão": é chamado como se fizesse parte de
// IServiceCollection (builder.Services.AddProducts()). Ele agrupa os
// registros da parte "produtos" da aplicação.
public static class ProductsExtensions
{
    public static IServiceCollection AddProducts(this IServiceCollection services)
    {
        // "quando um IProductsService for solicitado, forneça um ProductsService";
        // Singleton: uma única instância, compartilhada por todas as requisições
        services.AddSingleton<IProductsService, ProductsService>();
        return services;
    }
}
    • linha 6: uma classe estática, que contém apenas métodos estáticos;
    • linha 8: um método de extensão. A palavra-chave [this] antes do primeiro parâmetro permite chamá-lo como se fizesse parte do tipo desse parâmetro: [builder.Services.AddProducts()]. É assim que as bibliotecas do [ASP.NET Core] adicionam seus serviços ([AddControllers], [AddAuthentication]...), e é uma boa maneira de agrupar os registros de uma parte específica da aplicação;
    • linha 12: “quando uma classe solicitar um [IProductsService], forneça a ela um [ProductsService].” [Singleton] é o tempo de vida do serviço: uma única instância, criada na primeira requisição e compartilhada por todas as requisições. Existem outros dois tempos de vida: [Scoped] (uma instância por requisição) e [Transient] (uma nova instância a cada solicitação). O Capítulo 6 voltará a este assunto;
    • linha 13: o método devolve a lista de serviços para que as chamadas possam ser encadeadas.
