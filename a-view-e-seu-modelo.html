    4. A view e seu modelo

    Até aqui, as actions geraram suas próprias respostas. Em uma aplicação MVC, esse é o papel de uma view: um arquivo que descreve a página HTML, com marcadores para os dados que a action lhe passa — o modelo da view. O [ASP.NET Core MVC] usa o engine de views [Razor]: uma view é um arquivo [.cshtml], derivado de HTML, no qual se insere código [C#] precedido do caractere [@]. O [Razor] faz parte do framework: não há nada a instalar.

    using Example13.Models;
using Microsoft.AspNetCore.Mvc;

namespace Example13.Controllers;

public class ViewsController : Controller
{
    // View(model): a view que leva o nome da action (Views/Views/Index.cshtml)
    [HttpGet("/")]
    public IActionResult Index()
    {
        var model = new PageModel(
            "My first view",
            "This page was built by Razor, on the server.",
            DateTime.Now.ToString("HH:mm:ss"));
        return View(model);
    }

    // View(name, model): a view é escolhida pela action
    [HttpGet("hello/{name}")]
    public IActionResult Hello(string name)
    {
        if (name == "unknown")
        {
            Response.StatusCode = 404;
            return View("Unknown", name);
        }
        var model = new PageModel(
            $"Hello {name}",
            "This time, the action designated the view by its name.",
            DateTime.Now.ToString("HH:mm:ss"));
        return View("Index", model);
    }
}

    Vamos comentar este código:

    • linha 6: o controller deriva da classe [Controller], e não de [ControllerBase]: [Controller] acrescenta a [ControllerBase] tudo o que se relaciona a views (métodos [View], [ViewData], [TempData] etc.);
    • linhas 12–15: a action gera o modelo da view: um título, uma mensagem e a hora atual;
    • linha 16: [View(model)] devolve um [ViewResult]: a action não gera mais a resposta; em vez disso, designa uma view e lhe passa um modelo. Se nenhum nome de view for especificado, usa-se a view com o mesmo nome da action: [Index];
    • linhas 23–26: quando a view depende da requisição, a action escolhe a view. Aqui, o nome [unknown] exibe a view [Unknown], com código de status 404. O modelo dessa view é uma simples string;
    • linha 32: a action [Hello] especifica explicitamente a view [Index] pelo nome: duas actions compartilham a mesma view, com modelos diferentes.

    Onde o [ASP.NET Core] procura a view [Index] da action [ViewsController.Index]? Por convenção, em duas pastas, nesta ordem:

    • [Views/Views/Index.cshtml]: a pasta com o nome do controller (sem o sufixo [Controller]);
    • [Views/Shared/Index.cshtml]: a pasta que contém as views compartilhadas por todos os controllers (veja o Exemplo 15).

    Vamos comentar este código:

    • Linhas 2–5: um bloco de código chamado [@{ ... }] contém instruções [C#]. Ele não produz nada na página. As variáveis que declara ([total], [count]) podem ser usadas mais adiante na view;
    • linha 16: um valor [null] ([@Model.Nickname]) não exibe nada, sem erro;
    • Linhas 18–19: uma expressão [@...] faz o escape dos caracteres especiais do HTML ([<] torna-se [&lt;]...): o texto é exibido tal como está. [@Html.Raw(...)] o insere sem escape: ele é interpretado como HTML. [Html.Raw] só deve ser usado para HTML gerado pela aplicação, nunca para dados digitados por um usuário: o usuário poderia injetar HTML, ou até mesmo [JavaScript], na página (um ataque conhecido como [XSS], [cross-site scripting]);
    • Linhas 21–27: uma condição. Depois de [@if (...)], o conteúdo entre chaves é HTML: o [Razor] reconhece o início de uma tag e volta ao modo HTML. Retornamos ao [C#] por meio de [@];
    • linhas 32–40: um laço [for] [C#]. [var product = ...] é uma instrução [C#], [<li>] é HTML: o [Razor] alterna entre os dois sem nenhum marcador específico;
    • Linha 36: uma expressão explícita [@( ... )]. Os parênteses são obrigatórios sempre que a expressão contém espaços ou operadores (neste caso, o operador condicional [? :]);
    • linha 37: para escrever texto não formatado dentro de um bloco [C#], coloque-o na tag especial [<text>], que não aparece na página;
    • linha 38: [@:] faz o mesmo para o restante da linha;
    • linhas 45–51: uma lista vazia é simplesmente [if]. No bloco [else], já em modo [C#], [foreach] é escrito sem [@];
    • linha 55: as variáveis do bloco [@{ }] e expressões explícitas, incluindo uma chamada de método: [ToString("0.00")] formata um número com duas casas decimais;
    • linha 56: um caminho com pontos [@Model.Address.Street] e uma chamada de método [ToUpper()];
    • linha 57: [Razor] reconhece que um [@] colocado entre dois caracteres alfanuméricos não é código: [contact@example.com] é um endereço de e-mail. Para escrever um [@] que seria ambíguo, ele é duplicado: [@@].

    Vamos comentar este código:

    • linha 9: o serviço [HtmlEncoder] é o usado pelo [Razor] para escapar as expressões em [@]. Por padrão, ele deixa passar apenas os caracteres do alfabeto latino básico: é isso que codifica [é] como [&#xE9;] (e [€] como [&#x20AC;]). Substituímos esse serviço por um codificador que deixa passar todos os caracteres ([UnicodeRanges.All]). Os caracteres perigosos ([<], [>], [&], ["], [']) continuam escapados: a proteção contra injeção de HTML permanece intacta. Todos os exemplos seguintes, assim como o estudo de caso, incluem essa linha;
    • linha 14: um componente de middleware (veja o Capítulo 7) que serve os arquivos da pasta [wwwroot] do projeto: o arquivo [wwwroot/css/styles.css] é servido na URL [/css/styles.css]. Se o arquivo não existir, a requisição segue para os controllers;
    • linhas 16–19: um segundo serviço de arquivos estáticos. O framework CSS [Bootstrap] é comum a todos os exemplos: ele é armazenado uma única vez, na pasta [examples/common/bootstrap], e servido sob o prefixo [/bootstrap]. [PhysicalFileProvider] designa uma pasta do disco; [ContentRootPath] é a pasta do projeto. Assim, [examples/common/bootstrap/css/bootstrap.min.css] é servido na URL [/bootstrap/css/bootstrap.min.css]. O estudo de caso, por sua vez, coloca o [Bootstrap] em sua própria pasta, [wwwroot].

using System.Text.Encodings.Web;
using Microsoft.AspNetCore.Html;

namespace Example16.Helpers;

// funções C# comuns, chamáveis a partir das views: @Formats.Money(...)
public static class Formats
{
    // "keyboard" -> "KEYBOARD"
    public static string Uppercase(string? text) => (text ?? "").ToUpperInvariant();

    // um valor monetário em uma moeda, no formato do idioma atual (CultureInfo.CurrentCulture)
    // "C" = moeda; o objeto NumberFormatInfo define o símbolo da moeda
    public static string Money(decimal amount, string currency = "EUR")
    {
        var format = (NumberFormatInfo)CultureInfo.CurrentCulture.NumberFormat.Clone();
        format.CurrencySymbol = currency == "USD" ? "$" : "€";
        return amount.ToString("C", format);
    }

    // uma data por extenso, no idioma atual: "Wednesday, September 23, 2026"
    public static string Date(DateTime when) => when.ToString("D", CultureInfo.CurrentCulture);

    // um helper que constrói HTML: ele retorna um IHtmlContent, que o Razor não escapa.
    // Cabe então ao helper escapar os dados que insere (HtmlEncoder)
    public static IHtmlContent Badge(int stock)
    {
        var cssClass = stock > 0 ? "text-bg-success" : "text-bg-danger";
        var text = HtmlEncoder.Default.Encode(stock > 0 ? $"{stock} in stock" : "sold out");
        return new HtmlString($"<span class=\"badge {cssClass}\">{text}</span>");
    }
}

    4.7.1. Validação pelo navegador

    Os atributos [required], [maxlength], [min], [max], [type="email"]... instruem o navegador a validar o formulário antes de enviá-lo: o usuário é notificado imediatamente por meio de um tooltip, sem nenhuma comunicação de ida e volta com o servidor. É o comportamento obtido ao clicar no link “enable it” (http://localhost:5000/register?html5=true), que remove o atributo [novalidate] do formulário.

    Essa validação é uma conveniência, não uma medida de segurança: ela pode ser contornada simplesmente removendo o atributo [required] com as ferramentas de desenvolvedor do navegador ou enviando a requisição com [curl]. A validação no servidor continua sendo essencial. Por isso o exemplo desativa a validação do navegador por padrão: para demonstrar o funcionamento do servidor. O estudo de caso, por sua vez, mantém as duas: o atributo HTML5 por conveniência e a validação no servidor por segurança.

    4.8. Exemplo 20: o padrão Post/Redirect/Get

    Quando um formulário POST é enviado com sucesso, a action pode exibir uma página diretamente. O problema surge se o usuário atualizar essa página (tecla F5): o navegador reenvia o formulário e a operação é executada uma segunda vez (um pedido feito duas vezes, uma consulta marcada duas vezes...). O padrão Post / Redirect / Get (PRG) evita esse problema: uma action POST bem-sucedida não gera uma página; em vez disso, ela redireciona para uma página GET. Recarregar essa página apenas dispara outro GET, sem nenhum efeito.

    Resta um detalhe: a página GET deve exibir uma mensagem (“a tarefa foi adicionada”), embora essa mensagem tenha sido gerada pela action POST em outra requisição. Para resolver isso, o [ASP.NET Core] fornece o [TempData]: um dicionário cujo conteúdo persiste até a próxima requisição e desaparece assim que é lido. É uma mensagem flash. Por padrão, o [TempData] é armazenado em um cookie, criptografado pelo servidor.

public class ContactsService
{
    private readonly List<Contact> contacts =
    [
        new(1, "Marie Durand", "01 23 45 67 89"),
        new(2, "Paul Martin", "06 12 34 56 78"),
        new(3, "Philippe Jandot", "02 98 76 54 32"),
    ];

    // null se o contato não existir
    public Contact? Read(int id) => contacts.Find(c => c.Id == id);

    public Contact? Edit(int id, string name, string phone)
    {
        var index = contacts.FindIndex(c => c.Id == id);
        if (index < 0) return null;
        // um record é imutável: nós o substituímos por uma cópia modificada (com with)
        contacts[index] = contacts[index] with { Name = name, Phone = phone };
        return contacts[index];
    }

    public Contact Add(string name, string phone)
    {
        var contact = new Contact(++lastId, name, phone);
        contacts.Add(contact);
        return contact;
    }

    public Contact? Delete(int id)
    {
        var contact = Read(id);
        if (contact is not null) contacts.Remove(contact);
        return contact;
    }
}

    // confirmação dos formulários que carregam o atributo data-confirmation="..."
// Sem JavaScript, esses formulários são simplesmente enviados sem confirmação.
(() => {
  const modal = document.getElementById('confirmation-modal');
  const message = document.getElementById('confirmation-modal-message');
  let pending = null; // o formulário a enviar se o usuário confirmar

  // 1. interceptamos o envio dos formulários a confirmar
  document.querySelectorAll('form[data-confirmation]').forEach((form) => {
    form.addEventListener('submit', (event) => {
      event.preventDefault(); // o envio é suspenso
      pending = form;
      message.textContent = form.dataset.confirmation;
      modal.classList.remove('d-none'); // a janela aparece
    });
  });

  // 2. os dois botões da janela
  modal.addEventListener('click', (event) => {
    const action = event.target.dataset.action;
    if (action === 'yes') {
      pending.submit(); // envio, SEM disparar novamente o evento 'submit'
    } else if (action === 'no') {
      modal.classList.add('d-none');
      pending = null;
    }
  });
})();
    • linha 3: o código é envolvido em uma função executada imediatamente, para evitar a criação de variáveis globais;
    • linhas 9–14: o envio de cada formulário que possui o atributo [data-confirmation] é interceptado. [preventDefault()] suspende o envio; o formulário é guardado, a pergunta é colocada na janela ([textContent], e não [innerHTML]: a pergunta é exibida como texto, nunca interpretada como HTML) e a janela é exibida;
    • Linhas 19–25: “Sim” envia o formulário guardado. O método [submit()] de um formulário o envia sem disparar o evento [submit]: não há nova solicitação de confirmação. “Não” oculta a janela.

    Se o [JavaScript] estiver desativado, os formulários simplesmente são enviados sem confirmação: a aplicação continua funcionando. É o princípio do aprimoramento progressivo: o [JavaScript] acrescenta conveniência, mas não é essencial. O estudo de caso segue esse princípio (seu script, [wwwroot/js/app.js], acrescenta o tratamento do teclado: a tecla Esc e o foco).
